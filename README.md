# TradeMind India

India-first multi-broker portfolio, trading-journal, behavioural-risk and performance-intelligence platform.

> **Status:** first build session. The vertical slice — sign in → create a broker account → import a Zerodha
> Tradebook → validate/dedupe → generate trades → consolidated dashboard → open a trade → journal it →
> process score & rule compliance — is fully implemented with real deterministic logic. Every other nav
> item in the full product spec exists as a routed page (some backed by real seeded data, the rest behind a
> "Phase N" banner) so the app is fully clickable end to end. See **Scope & roadmap** below.

## Tech stack

Next.js 15 (App Router) · TypeScript (strict) · Tailwind CSS · shadcn/ui-style components · PostgreSQL ·
Prisma · Auth.js v5 · Redis (wired, unused this phase) · Zod · TanStack Table · React Hook Form · Recharts ·
Papa Parse / SheetJS · S3-compatible storage (MinIO locally) · Vitest · Playwright · Docker Compose.

## Prerequisites

- Node.js 20+
- pnpm 9+
- Docker Desktop (for Postgres/Redis/MinIO)

## Setup

```bash
pnpm install
cp .env.example .env          # generate NEXTAUTH_SECRET and ENCRYPTION_KEY (see comments in the file)
docker compose up -d          # postgres:5434, redis:6381, minio:9010/9011 — non-default ports, see below
pnpm prisma migrate dev       # applies migrations under prisma/schema/migrations
pnpm db:seed                  # creates demo@trademind.in / Demo@1234 with real imported demo trades
pnpm dev                      # http://localhost:3000
```

**Why non-default ports?** `docker-compose.yml` maps Postgres to `5434`, Redis to `6381`, and MinIO to
`9010`/`9011` on the host, to avoid clashing with other local services. If you don't have that problem,
feel free to remap to the defaults in both `docker-compose.yml` and `.env`. Also prefer `127.0.0.1` over
`localhost` in connection strings — on some Windows setups Node resolves `localhost` to `::1` first, which
Docker Desktop's port publishing doesn't always answer on.

### Environment variables

See `.env.example` for the full list with inline explanations. Summary:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Postgres connection string |
| `NEXTAUTH_URL`, `NEXTAUTH_SECRET`, `AUTH_TRUST_HOST` | Auth.js session signing |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Optional — Google login only registers when both are set |
| `NEXT_PUBLIC_GOOGLE_LOGIN_ENABLED` | Client-side flag to show/hide the Google button; keep in sync with the above |

| `RAZORPAY_*` | Unused stub — Billing page is read-only this phase |
| `ENCRYPTION_KEY` | Reserved for encrypting future OAuth broker tokens; nothing writes to it yet |

## Architecture

```
prisma/schema/*.prisma   Multi-file Prisma schema, one file per domain (auth, broker, market, import,
                          trading, portfolio, journal, risk, ai, reporting, subscription). ~50 entities
                          covering the full product spec; only the vertical slice's tables carry real
                          business logic this phase — the rest are minimal-but-real shapes so later
                          phases don't need a destructive migration.
prisma/seed.ts            Seeds roles/brokers/instruments/a demo user, then runs the REAL import
                          pipeline against fixtures/zerodha-tradebook-sample.csv — demo data is
                          generated by actual code, not hardcoded.

src/lib/calculations/     Deterministic, pure, Vitest-covered financial math (Decimal.js, never
                          native `number`): weighted average price, lot-level P&L, the Zerodha equity
                          charge engine, process score, rule-compliance evaluation.
src/lib/brokers/          BrokerAdapter interface + registry. Only ZERODHA is implemented
                          (CSV/XLSX Tradebook parser); other brokers are registered as
                          `isImplemented: false` stubs.
src/lib/import/           dedup.ts (fingerprint-based duplicate detection), trade-grouping.ts (FIFO
                          matching of executions into round-trip trades, pure function, fully unit
                          tested), preview.ts (read-only dry-run for the wizard), pipeline.ts
                          (orchestrates the whole import → trades → charges → rule evaluation flow).
src/lib/queue/            ioredis client + a defined (unconsumed) BullMQ queue. The import pipeline
                          runs synchronously inside a Server Action this phase; its signature is
                          worker-ready for when a queue consumer is added.
src/lib/auth/              Auth.js v5 config. Credentials (bcrypt) + conditional Google provider,
                          JWT session strategy (required alongside Credentials — see comment in
                          auth.ts), RBAC helpers for role-gated pages.

src/server/services/       Pure business logic, framework-agnostic, called from both Server Actions
                          and pages.
src/server/actions/        Thin `"use server"` wrappers over the services above.

src/app/(auth)/            Login/Register.
src/app/(onboarding)/      Single abbreviated onboarding page (not the full 11-step wizard).
src/app/(app)/             Every authenticated route from the product spec's navigation tree.
                          Wired-with-real-data pages: Dashboard, Broker Accounts, Imports (wizard +
                          history), Closed Trades, Open Positions, Executions, Trade Detail (journal +
                          rule compliance + process score), Trading Rules, Rule Violations, Risk
                          Dashboard, Trading Calendar, Charges Analysis, Reports, Holdings, Investment
                          Thesis, Daily Journal, Notifications, Settings, Billing.
                          Everything else renders with seeded illustrative data behind a `PhaseNotice`
                          banner naming the future build phase, per the spec's requirement that every
                          page show realistic demo data rather than a blank stub.

fixtures/                  Sample Zerodha Tradebook CSV (26 rows: intraday round trips, a multi-day
                          delivery position, a still-open position, two exact-duplicate rows to prove
                          dedup, one malformed row to prove validation) — used by both the seed script
                          and the Playwright smoke test.
tests/e2e/                  Playwright smoke test covering the full vertical slice end to end.
```

## Deterministic-calculation guarantees

Per the product requirements, an LLM never computes P&L, charges, returns, drawdowns or scores. Every
number shown in the UI comes from a pure TypeScript function in `src/lib/calculations/`, operating on
`decimal.js` `Decimal` (never native `number`, to keep the gross/net-P&L-and-charges reconciliation exact),
covered by unit tests in `__tests__/` alongside each module. Where there's genuinely insufficient data to
compute a meaningful number (e.g. a trade with no applicable rules and no journal), the functions return
`null` rather than fabricating a score — this is exercised explicitly in the process-score tests.

## Known simplifications this phase (see the plan file for full rationale)

- Charge rates are hardcoded named constants, not a versioned `ChargeRate` DB model yet.
- Stamp duty defaults to the Maharashtra rate (the real rate depends on the trader's state of registration).
- Intraday vs. delivery is classified heuristically (same-day full close ⇒ intraday) because Zerodha's
  Tradebook CSV has no explicit product-type column.
- Re-importing a file recomputes all trades for the touched instruments from scratch, which would also
  drop any journal entries on those trades — fine for this phase's single-import demo flow; multi-import
  reconciliation that preserves journaled trades is a later-phase improvement.
- No inline ambiguous-row edit UI — invalid rows are shown with reasons but not editable in-app.
- Import runs synchronously in the Server Action; BullMQ is wired but no worker process is started.
- 2FA (`TwoFactorSecret`) and device session (`DeviceSession`) tables exist with no management UI yet.
- Dashboard omits unrealized P&L / live portfolio value entirely (no market-data feed exists yet) rather
  than showing a fabricated number.

## Scope & roadmap

This build follows the product spec's own 5-phase MVP ordering. Phase 1 (this session) covers
architecture, auth, the full schema, and the named vertical slice. Later phases (not built yet, but the
schema and adapter interfaces are already shaped for them): more broker adapters (Dhan, Upstox, Angel One,
Fyers, Groww), automatic options-strategy grouping, the Behavioural Loss Engine, Profit Give-Back Detector,
cross-broker risk intelligence, the Scenario Simulator, the AI Coach, full tax/reporting exports, and
Razorpay billing.

## Testing

`pnpm test` runs 45 Vitest unit tests covering weighted average price, lot-level P&L, the Zerodha charge

## Security notes

- **No broker credentials are ever stored.** `BrokerConnection.accessTokenEncrypted` /
  `refreshTokenEncrypted` are reserved for a future official OAuth broker integration and remain `null` for
  every CSV-based account created this phase.
- Passwords are hashed with bcrypt (cost 12), never stored or logged in plaintext.
- Auth.js v5 uses the Credentials provider, which requires the `jwt` session strategy (Auth.js does not
  support `database` sessions with Credentials sign-in) — see the comment in `src/lib/auth/auth.ts`. A
  `DeviceSession` row is still written on every credentials sign-in so Settings → Security has real data to
  show once a device-management UI is built.
- Middleware runs on the Node.js runtime, not Edge, since `auth.ts` depends on Prisma and bcryptjs — both
  incompatible with the Edge runtime.
- Row-level isolation: every Prisma query in `src/server/services/` filters by the authenticated
  `session.user.id`; there is no endpoint that reads another user's data by guessable ID.
- `RiskProfile`, journal entries and behavioural data are only ever queried scoped to the current user —
  the Mentor/Accountant role split from the product spec is represented in the schema (`RoleKey` enum) but
  cross-user sharing (mentor viewing an invited trader's data) is not implemented this phase, so no such
  cross-user read path exists yet to secure.
- Uploaded broker files go to a **private** MinIO/S3 bucket (no public/anonymous access); downloads happen
  server-side only.
- Original broker `Execution` records are immutable — corrections happen by rolling back and re-importing,
  never by editing a row in place (no update path exists on that model).
- CSRF: Auth.js's built-in CSRF token protects the credentials sign-in flow; all other mutations go through
  Next.js Server Actions, which have built-in CSRF protection via same-origin `Origin`/`Referer` checks.
- Secrets (`NEXTAUTH_SECRET`, `ENCRYPTION_KEY`, DB/MinIO credentials) live in `.env`, which is git-ignored;
  `.env.example` documents every variable without real values.

## Deployment notes (MVP)

This build has been developed and tested against local Docker Compose services. For a first deployment:

1. Provision managed Postgres, Redis and S3-compatible storage (or self-hosted equivalents).
2. Set all variables from `.env.example` against those managed services; generate fresh `NEXTAUTH_SECRET`
   and `ENCRYPTION_KEY` values (never reuse the local dev secrets).
3. Run `pnpm prisma migrate deploy` (not `migrate dev`) against the production database.
4. Run `pnpm build && pnpm start`, or containerize with a standard Next.js Dockerfile (not included this
   phase — this repo currently only containerizes the dev-time infra, not the app itself).
5. Point the S3 bucket's access policy to private-only, matching the local MinIO setup.
6. Do not run `pnpm db:seed` against production — it's a development/demo convenience only.
